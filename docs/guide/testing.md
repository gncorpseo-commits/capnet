> 무엇이 증거로 인정되는가 · 무엇을 자동으로 막는가.

## 1. 왜 지금인가

이 리포는 오래 **테스트 0 · CI 0** 이었다. 스키마 제약이 대부분의 하중을 받으니
애플리케이션 테스트의 값어치가 낮다는 판단이었고, 그건 지금도 부분적으로 맞다.

그런데 SD-007·SD-013 을 하면서 **DB 밖에서 판정하는 도구**가 셋 생겼다.

| 도구 | 무엇을 지키나 | 틀리면 |
|------|---------------|--------|
| `app/migrate_lint.py` | 절대규칙 1·2 (제약 약화 · 수기 스냅샷 INSERT) | 마이그레이션 경로로 제약이 빠져나간다 |
| `scripts/check_golden_sha.py` | 골든셋 선언부 정합 | capability 가 리포에 없는 골든셋을 가리킨다 (SD-013) |
| `app/migrate.py` | 계보·체크섬·잠금 | 기존 볼륨 업그레이드가 조용히 어긋난다 |

이것들은 **제약이 잡아 주지 않는다.** 그래서 여기부터 테스트를 넣었다.

## 2. 쓰는 법

```bash
scripts/run_tests.sh              # 단위 테스트 + 골든셋 정합
python3 -m unittest discover -s tests -v
```

**의존성이 없다.** 표준 라이브러리 `unittest` 만 쓴다 — 이 리포에는 pip 가 없는 개발 환경이 있고,
새 의존성은 `CLAUDE.md` 상 먼저 물어야 한다. pytest 가 필요해지면 그때 논의한다.

예외는 **`capreq/tests`** 하나다. capreq 는 독립 모듈이라 자기 런타임이 있고,
그 테스트는 `tests/` 밖에 있어 위 명령에 잡히지 않는다. 따로 돌린다:

```bash
pip install "httpx>=0.27" "fastapi>=0.110" "python-multipart>=0.0.9"
PYTHONPATH=capreq/src python3 -m unittest discover -s capreq/tests -p "test_*.py"
```

**세 개를 다 깔아야 한다.** 이 줄은 CI 의 `capreq` 잡과 **글자 그대로 같아야 하고**,
`tests/test_testing_doc.py` 가 그것을 본다.

> 여기가 실제로 어긋나 있었다 (2026-09-01). 이 문서는 오래 **`httpx` 하나**만 적었는데
> 서버 경로 검사가 들어오면서 CI 는 셋을 깔게 됐다. 문서대로 `httpx` 만 깔고 돌리면
> `python-multipart` 가 없어 **첨부 검사 3건이 실패한다** — 제품이 아니라 설치가 틀린 것인데,
> 그걸 제품 결함으로 오해하기 딱 좋다. 실제로 이번에 그렇게 오해했다.

`node` 도 필요하다 — 없으면 렌더러·흐름 프로브 6건이 **skip 된다** (§4.6).
`skip 은 통과가 아니다.` 숫자를 적을 때는 건너뛴 개수를 같이 적는다.

`run_tests.sh` 가 이것을 부르지 않는 것은 의도다 — 이 셋이 없는 환경에서 전체 검증이
통째로 실패하면 안 된다. CI 는 잡을 따로 둬서 항상 돌린다 (§4).

## 3. 지금 있는 것

**개수도, 파일 목록도 여기 적지 않는다.** 이 표는 한때 파일 **둘**만 적고 있었는데
그 사이 `tests/` 는 **스물아홉**이 됐다 (2026-09-01 실측). 손으로 세는 목록은 반드시 낡는다 —
`test_doc_counts` 가 통합 검사 개수를 못박지 못하게 하는 것과 같은 이유다.

무엇이 있는지는 **파일이 말한다**:

```bash
ls tests/test_*.py
python3 -m unittest discover -s tests -v    # 이름과 docstring 이 곧 목록이다
```

처음 둘은 이 문서가 생긴 이유라 남겨 둔다 — **왜** 그것부터 짰는지가 §1 이다.

| 파일 | 무엇을 |
|------|--------|
| `tests/test_migrate_lint.py` | 금지 패턴 · 주석 오탐 · `INSERT … SELECT` 정상 통과 · 허용 표식의 **범위** · 파일명/번호 규칙 |
| `tests/test_golden_sha.py` | 정본화 방식 · 선언부 4곳 일치 · 파서가 조용히 통과하지 않는지 · `split=holdout` 유지 |

여기 이름이 적힌 파일이 실제로 있는지는 `tests/test_testing_doc.py` 가 본다.
**이름을 바꾸면 문서가 걸린다.**

### 골든 픽스처를 따로 두지 않았다

`test_golden_sha.py` 는 **리포에 실제로 커밋된 파일**을 본다. 막으려는 사고가 정확히
「커밋된 선언부가 서로 어긋나는 것」이라, 픽스처를 따로 두면 사고를 못 잡는다.

`test_migrate_lint.py` 도 마찬가지로 `migrations/` 전체를 실제로 lint 한다.

### 오탐도 테스트한다

검사기가 정상 SQL 을 막으면 아무도 안 쓴다. 그래서 다음이 **통과해야 한다**고 못박았다.

- `INSERT INTO gate_run … SELECT …` (정상 경로)
- 주석 안의 `DROP CONSTRAINT` (경위 설명)
- PL/pgSQL `DO $$ BEGIN … END $$` (트랜잭션 제어가 아니다)

### 허용 표식의 범위

`-- capnet:allow-constraint-change` 는 **절대규칙 1 에만** 쓰인다.
절대규칙 2(수기 스냅샷)와 트랜잭션 제어는 표식이 있어도 막힌다. 테스트가 이걸 고정한다.

## 4. CI (`.github/workflows/ci.yml`)

| job | 무엇을 |
|-----|--------|
| **unit** | `tests/` 단위 테스트 + `check_golden_sha.py` + **`check_release.sh`(G9 제출 zip 사전 검증)** + `check_submission.py`. **의존성 설치 없음** |
| **capreq** | `capreq/tests` — `httpx`·`fastapi`·`python-multipart` 와 `node` 를 설치한다 (§2 와 같은 줄). 잡을 따로 둔 이유는 위 `unit` 의 「설치 없음」을 지키기 위해서다 |
| **migrate** | postgres 서비스로 **실제 적용**. 마이그레이션 **7단계** + **통합 검사 전부**(검사마다 깨끗한 DB) |

> **이 절은 `ci.yml` 의 단계와 하나씩 대응한다** — `tests/test_ci_claims_match_the_workflow.py`
> 가 대조한다. 예전에는 `unit` 의 제출 zip 검증과 `migrate` 의 마지막 단계가
> **빠져 있었다** (큐 #59). 여기서 그 단계 이름을 다시 적지 않는다 — 적으면 아래
> 목록에서 지워도 이 문장 때문에 검사가 통과한다:
> 「CI 가 본다」고 적힌 목록이 실제보다 짧으면, 안 적힌 단계는 **없는 것처럼 읽힌다.**

> 통합 검사 **개수를 적지 않는다.** 능력·강제 경로를 더할 때마다 느는 값이라
> 문서에 못박으면 다음 사람이 숫자만 고치게 된다 (`test_doc_counts` 가 같은 이유로
> `check_*` 개수를 금지한다). 몇 개인지는 `run_integration.sh` 출력이 말한다.

migrate job 이 보는 것:

1. **baseline 가드** — 빈 DB 에서 `up` 이 거부되고 **테이블이 하나도 안 생기는지**
2. schema + seed 적용 (새 볼륨 경로 = initdb 가 하는 일)
3. `verify → up → verify → up` — 마지막이 「적용할 것 없음」이어야 한다 (멱등)
4. **새 볼륨이면 증적 드리프트 0** — seed 와 매니페스트가 어긋나면 여기서 걸린다
5. **체크섬 잠금** — 적용된 파일을 고치면 `verify`·`up` 이 둘 다 거부하는지
6. **기존 볼륨 경로** — 구 sha 로 되돌린 뒤 `0003` 이 다시 올려주는지
7. **새 볼륨에는 placeholder Agent 의 라우팅 증서가 없다** (SD-015)

6단계는 CI 를 마이그레이션 **양쪽 경로**(빈 볼륨 · 기존 볼륨)의 회귀 시험으로 만든다.
7단계는 seed 가 라우팅 가능한 placeholder 를 남기지 않는지 본다 — `#0005` 가 멈추던 자리다.
이 리포에서 가장 깨지기 쉬운 지점이 거기였다.

## 4.5 통합 검사는 검사마다 깨끗한 DB 를 받는다

통합 검사는 `scripts/run_integration.sh` 가 돌린다 — `tests/integration/check_*.py` 를
이름 순으로 **전부** 집어간다. 파일을 놓기만 하면 CI 가 돈다 (등록부가 따로 없다).

```bash
scripts/run_integration.sh                    # 전부
scripts/run_integration.sh check_revocation   # 하나만
```

### 왜 러너가 필요했나

대부분은 SAVEPOINT + ROLLBACK 으로 스스로 격리한다. 그런데 **`check_revocation` 은 커밋해야 한다** —
배정·폐기·복권은 각각 다른 트랜잭션이고, **그 경계를 넘나드는 것이 바로 그 검사가 보는 계약**이다.
트랜잭션 안에 가둘 수 없다.

그래서 그 검사가 남긴 상태가 뒤 검사를 오염시켰다. 처음 대응은 반창고였다 —
「뒤 검사의 SETUP 을 멱등하게」·「앞 검사가 뒷정리」. 그건 **쌍마다 붙이는 대응**이라
검사가 늘면 조합이 늘고, **순서 가정이 코드 어디에도 적히지 않은 채** 남는다.

### 템플릿 데이터베이스

완전히 마이그레이션된 템플릿을 한 번 만들고, 검사마다 `CREATE DATABASE ... TEMPLATE` 로 복제한다.
PostgreSQL 에서 이건 파일 복사라 빠르다. DROP 하지 않는다 — 서버(CI 서비스 컨테이너)가 일회용이다.

- 순서 의존이 **사라진다**
- 커밋하는 검사가 마음껏 커밋해도 된다
- **반창고를 걷어냈다** — 멱등 SETUP·뒷정리 코드를 지웠다

### 구조가 일한다는 증명

반창고를 뗀 상태에서:

| 실행 | 결과 |
|------|------|
| 공유 DB · `check_revocation` 먼저 | `check_pg_violations` **실패** (오염) |
| 템플릿 격리 · 기본 순서 | 5/5 |
| 템플릿 격리 · 오염원 맨 앞 | 5/5 |
| 템플릿 격리 · 역순 | 5/5 |
| 템플릿 격리 · 같은 검사 두 번 | 3/3 |

첫 줄이 중요하다 — **격리를 빼면 실제로 깨진다.** 그래야 격리가 값을 하는 것이다.

## 4.6 CI 밖에서 도는 것 두 부류 — **없으면 건너뛴다**

전부 CI 에 넣을 수는 없다. 어떤 검사는 **CI 에 없는 것**(Ollama · 살아 있는 스택)을 필요로
한다. 그럴 때 이 저장소가 쓰는 방식은 둘이다 — **건너뛰거나, 수동 도구로 두거나.**

### 건너뛴다 — `node` 실행 프로브

`chat.html` 의 `<script>` 를 **최소 DOM 스텁으로 실제로 돌린다.** `npm` 패키지는 0 이다.

| 프로브 | 무엇을 |
|---|---|
| `capreq/tests/chat_render_probe.js` | 렌더러를 호출해 **만들어진 DOM** 을 단언 (능력별 결과 모양) |
| `capreq/tests/chat_flow_probe.js` | **경로 전체** — 보내기 → 라우팅 → 폴링 → 결과 |

`capreq/tests/test_chat_render.py` 가 `node` 를 찾아 돌리고, **없으면 `skip`** 한다.
그래서 루트 `run_tests` 의 「의존성 설치 없음」이 깨지지 않는다. CI 의 `capreq` 잡에는
`setup-node` 가 있으므로 **거기서는 실제로 돈다.**

**왜 문자열 검사로 부족했나.** 옆에 `test_chat_html_unit.py` 가 있는데 그건 부분 문자열
검사라 **「반쯤 지운 렌더러」를 통과시킨다** — 실제로 재현했다(분기만 남기고 몸통을 지우면
문자열 검사는 통과하고 실행 검사는 7종으로 잡는다).

### 수동 도구로 둔다 — 라우팅 벤치

`scripts/route_bench.py` 는 **Ollama 와 등록된 능력**이 있어야 돈다. CI 에 넣지 않는다.

```bash
PYTHONPATH=capreq/src python3 scripts/route_bench.py --set holdout --repeats 5
```

**판정은 홀드아웃으로만** 한다(기본값). 설명을 손보면서 같은 프롬프트로 재면 반드시
좋아지기 때문이다 — 실제로 어떤 수정안이 튜닝 세트에서 55→60 이었는데 홀드아웃에서는
**순 효과 0** 이었다. 숫자를 쓸 때의 규율은 [`measured-claims.md`](./measured-claims.md).

### 수동 도구로 둔다 — **제품 입구** 종단

`scripts/capreq_demo.sh` 는 사람이 실제로 쓰는 입구를 그대로 밟는다 —
문장 + 첨부 → 라우팅 → **Core 중개 업로드** → 승인 Node 실행 → 증적.

```bash
scripts/capreq_demo.sh
```

**왜 필요했나.** 다른 `*_demo.sh` 는 전부 **Core 를 직접** 부른다. 그래서 입구가 끊겨도
전부 초록이었다 — 실제로 **첨부가 한 번도 동작하지 않았고**(`7936a0f`), 단위 검사도
`chat_flow_probe.js` 도 통과하고 있었다. `fetch` 를 스텁으로 막기 때문이다.
손으로 종단을 재고서야 잡혔고 **그 실측은 어디에도 남지 않았다.** 이제 남는다.

**종료 코드가 배선과 라우팅을 가른다.**

| 코드 | 뜻 |
|---|---|
| 0 | 경로가 이어졌다 |
| **1** | **배선이 끊겼다** — 서비스 없음 · `input_id` 누락 · 증적 없음. 고칠 버그다 |
| **2** | **라우팅이 빗나갔다** — 배선은 멀쩡한데 뽑힌 능력이 그 첨부를 못 다룬다 |

둘을 같이 세면 검사가 흔들린다 — 로컬 LLM 은 매번 같지 않다. **정확도는 여기서 재지
않는다** (`route_bench` 가 홀드아웃으로 잰다). 스크립트가 검사를 빠뜨리지 않는지는
`tests/test_capreq_demo.py` 가 본다.

### 이 부류를 늘릴 때의 규칙

**「없으면 skip」은 「없으면 조용히 통과」와 다르다.** skip 은 **몇 개가 건너뛰어졌는지**
출력에 남고, 프로브가 **몇 종을 단언했는지**도 파이썬 쪽에서 다시 본다
(`test_probe_actually_asserted_things`). 0 건을 통과시키는 상태를 막는 것이 핵심이다.

**그래도 가려졌다 (2026-09-01).** 환경이 바뀌어 `node` 가 사라졌고, capreq 스위트가
**68 → 50 ran / 6 skipped** 로 줄었다. 빠진 6건이 바로 위 표의 실행 프로브 —
문자열 검사가 못 잡는 것을 잡으라고 넣은 것들이다. 출력에 `skipped=6` 이라 적혀 있었지만
**아무도 그 숫자를 읽지 않았다.** `OK` 는 초록색이고 skip 은 회색이다.

그래서 사유를 **허가제**로 만들었다 — `tests/test_skip_reasons.py`.

- 새 `skip` 의 사유 문자열은 `ALLOWED` 에 **왜 괜찮은지**와 함께 적어야 한다
- 안 쓰이는 사유가 남으면 걸린다 (지운 검사의 흔적)
- **개수는 못박지 않는다** — 환경마다 다른 것이 정상이다

묻게 하려는 것은 하나다: **이건 그 환경에 없는 것인가, 아니면 깨진 검사를 덮는 것인가?**

숫자를 적을 때는 **건너뛴 개수를 같이 적는다.** 「capreq 68」과 「capreq 68 (건너뜀 6)」은
다른 말이다.

## 5. 아직 없는 것 (정직하게)

- **게이트 사슬 통합 테스트.** `demo.sh`·`proof_ab.sh`·`sanity.sh` 는 여전히 수동이다.
  torch 가 필요해 CI 시간이 크게 늘어난다 — 넣으려면 별도 판단이 필요하다.
- **lint/포맷 도구.** `ruff` 설정이 없다. 개발 환경에 pip 가 없어 보류했다.
- **`regate.sh` 테스트.** Node·가중치가 있어야 해서 단위 테스트가 어렵다.
- **실제 브라우저.** 위 프로브는 최소 스텁이라 **CSS·레이아웃과 파일 선택기의 OS
  상호작용은 못 본다.** Playwright 는 새 의존성이라 아직 안 들였다 —
  「브라우저에서 봤다」고 쓰지 않는 이유다.

새 판정 도구를 만들면 **테스트를 같이 넣는다.** 그게 이 문서의 요점이다.
