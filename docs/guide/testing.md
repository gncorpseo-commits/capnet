## 1. 왜 지금인가

이 리포는 오래 **테스트 0 · CI 0** 이었다. 스키마 제약이 대부분의 하중을 받으니
애플리케이션 테스트의 값어치가 낮다는 판단이었고, 그건 지금도 부분적으로 맞다.

그런데 SD-007·SD-013 을 하면서 **DB 밖에서 판정하는 도구**가 셋 생겼다.

| 도구 | 무엇을 지키나 | 틀리면 |
|------|---------------|--------|
| `app/migrate_lint.py` | 절대규칙 1·2 (제약 약화 · 수기 스냅샷 INSERT) | 마이그레이션 경로로 제약이 빠져나간다 |
| `scripts/check_golden_sha.py` | 골든셋 선언부 정합 | capability 가 리포에 없는 골든셋을 가리킨다 (SD-013) |
| `app/migrate.py` | 계보·체크섬·잠금 | 기존 볼륨 업그레이드가 조용히 어긋난다 |

이것들은 **제약이 잡아 주지 않는다.** 그래서 여기부터 테스트를 넣었다.

## 3. 지금 있는 것

| 파일 | 수 | 무엇을 |
|------|-----|--------|
| `tests/test_migrate_lint.py` | 33 | 금지 패턴 · 주석 오탐 · `INSERT … SELECT` 정상 통과 · 허용 표식의 **범위** · 파일명/번호 규칙 |
| `tests/test_golden_sha.py` | 15 | 정본화 방식 · 선언부 4곳 일치 · 케이스 40건 · 파서가 조용히 통과하지 않는지 · `split=holdout` 유지 |

### 골든 픽스처를 따로 두지 않았다

`test_golden_sha.py` 는 **리포에 실제로 커밋된 파일**을 본다. 막으려는 사고가 정확히
「커밋된 선언부가 서로 어긋나는 것」이라, 픽스처를 따로 두면 사고를 못 잡는다.

`test_migrate_lint.py` 도 마찬가지로 `migrations/` 전체를 실제로 lint 한다.

### 오탐도 테스트한다

검사기가 정상 SQL 을 막으면 아무도 안 쓴다. 그래서 다음이 **통과해야 한다**고 못박았다.

- `INSERT INTO gate_run … SELECT …` (정상 경로)
- 주석 안의 `DROP CONSTRAINT` (경위 설명)
- PL/pgSQL `DO $$ BEGIN … END $$` (트랜잭션 제어가 아니다)

### 허용 표식의 범위

`-- capnet:allow-constraint-change` 는 **절대규칙 1 에만** 쓰인다.
절대규칙 2(수기 스냅샷)와 트랜잭션 제어는 표식이 있어도 막힌다. 테스트가 이걸 고정한다.

## 4. CI (`.github/workflows/ci.yml`)

| job | 무엇을 |
|-----|--------|
| **unit** | 단위 테스트 + `check_golden_sha.py`. 의존성 설치 없음 |
| **migrate** | postgres 서비스로 **실제 적용**. 아래 6단계 + 폐기 경로 + PG 위반 19종 |

migrate job 이 보는 것:

1. **baseline 가드** — 빈 DB 에서 `up` 이 거부되고 **테이블이 하나도 안 생기는지**
2. schema + seed 적용 (새 볼륨 경로 = initdb 가 하는 일)
3. `verify → up → verify → up` — 마지막이 「적용할 것 없음」이어야 한다 (멱등)
4. **새 볼륨이면 증적 드리프트 0** — seed 와 매니페스트가 어긋나면 여기서 걸린다
5. **체크섬 잠금** — 적용된 파일을 고치면 `verify`·`up` 이 둘 다 거부하는지
6. **기존 볼륨 경로** — 구 sha 로 되돌린 뒤 `0003` 이 다시 올려주는지

6단계는 CI 를 마이그레이션 **양쪽 경로**(빈 볼륨 · 기존 볼륨)의 회귀 시험으로 만든다.
이 리포에서 가장 깨지기 쉬운 지점이 거기였다.
