### 1.1 3번은 "미구현"이 아니라 "미실행"

지정 실행(M14) 배관은 처음부터 **있었다.** 없던 것은 실행 이력이고, 2026-08-08에 채워졌다.

| 조각 | 상태 | 위치 |
|------|------|------|
| `task.requested_agent_id` (FK → `agent`) | ✅ | `spec/schema.sql:355` |
| claim이 지정 Agent만 고르는 조인 | ✅ | `claim.py` `CLAIM_SQL` — `AND (t.requested_agent_id IS NULL OR acp.agent_id = t.requested_agent_id)` |
| 지정 Agent도 **게이트 통과 강제** | ✅ | 같은 조인이 `agent_capability_passed`를 거친다 — 미통과 Agent는 지정해도 할당 안 됨 |
| `POST /v1/tasks` `requestedAgentId` | ✅ | `main.py` · `openapi.yaml` · **`demo.sh`가 A로 이미 사용 중** |
| A/B 교차 실행·비교 절차 (UC-7) | ✅ **신설** | `scripts/proof_ab.sh` — 실게이트 2건 + 교차 할당 + 라벨 비교 |
| `task.proof_run_id` 채우는 코드 | ❌ | 컬럼만 존재. A/B 쌍을 한 증명 run으로 묶을 식별자 — **남은 유일한 구현 공백** |

3번을 막던 것은 **2번 하나**였고, Agent B가 게이트를 통과하자 교체 할당은 기존 배관으로 그대로 실행됐다.
남는 구현 공백은 `proof_run_id` 기록 하나뿐이다 — A/B 쌍을 하나의 증명 run으로 묶는 식별자가 아직 비어 있다.

### 1.2 4번 측정의 한정 (중요)

`scripts/score_n300.*`는 `docker compose run --rm --no-deps`로 `app.score_gate`를 **직접** 실행하고,
`scripts/compare_ab.py`는 그 결과 **점수 JSON 두 개**를 읽어 비교한다. DB를 열지 않는다.

- **같은 것:** 채점기는 실게이트와 동일 모듈(`app.score_gate`) · 동일 골든셋 · 동일 전처리(32×32)
- **다른 것:** `gate_run` → `gate_run_passed` → `agent_capability_passed` → `assignment` **사슬을 타지 않는다**

따라서 0.0467은 **"두 가중치의 정확도가 비슷하다"**는 사실이지,
**"계약을 통과한 Agent를 CapNet이 바꿔 끼워도 결과가 등가다"**는 아직 아니다. 후자가 §7.1이 요구하는 명제다.

> 이 구분은 보고서·영상에서도 유지한다. 사슬 밖 측정을 사슬 안 증명으로 말하면 D1(증명 대상 = Capability 추상화 성립)이 무너진다.

### 1.3 통과율 밴드

§7.2 Kill 판정은 편차와 **통과율 20–80%**를 함께 본다. 통과율은 현재 **미실측**이다 —
게이트를 통과시킨 Agent 모집단이 A 하나뿐이라 비율을 정의할 수 없다.

### 2.2 P1-3 모집단을 어디서 얻는가

새 백본을 5개 학습할 필요는 없다. 이미 있는 것으로 밴드를 만든다.

- sanity floor 3종(상수·난수·스키마 위반) — **반드시 FAILED** (하한 고정)
- Agent A(80ep) · B(40ep) — PASSED 기대
- 저epoch 변형(예: 5ep·10ep) — 경계 근처 후보

통과율이 100%면 골든셋이 약한 것이고, 0%면 강한 것이다. **밴드 밖이면 그것이 §7.2의 판정**이며, 실패로 적는다.

### 3.2 P2-1 에서 로드맵이 틀렸던 곳 (2026-08-11)

「스키마에 이미 있음 · DDL 추가가 아니라 운용」은 **절반만 맞았다.** 행은 맞고, 한 칸을 빠뜨렸다.

`domain_min_compatible` 은 task 의 privacy_rank 가 `capability.trust_domain_min` 이상일 것을 요구한다.
`image.classify@1` 의 min 은 `team`(3) 이라 **tenant Task(2)는 그 계약을 원천적으로 쓸 수 없다** — Node 를 아무리 넣어도 안 된다.
그래서 tenant 유통에는 `trust_domain_min <= tenant` 인 **계약이 선행**한다. 기존 계약을 낮추지 않고 `image.classify@2` 를 추가했다.

그리고 tenant Node 를 넣자마자 **claim 버그(SD-016)**가 드러났다 — `CLAIM_SQL` 이 호환 행렬을 후보 단계에서 보지 않아,
호환 Node 가 있는데도 예외로 Task 가 굶었다. 라우팅 차단 보장은 지켜졌고 깨진 것은 가용성이다.
**단일 도메인 함대에서는 보이지 않던 결함**이라, P2-1 의 진짜 값어치는 여기 있었다.

### 3.1 여기서 스키마 동결이 깨진다

기획서 §16: *v4.4를 Phase 1 DDL 기준으로 둔다. 이후 변경은 마이그레이션 이슈로만.*

P2-4는 v4.4 동결을 처음으로 건드리는 작업이다. `CLAUDE.md` 절대규칙 1(제약 약화 금지)은 유지되고 **추가는 허용**되므로 경로는 있으나, 다음이 선행한다.

1. 마이그레이션 도구·순서 결정 (현재 `init.sql` 일괄 적용뿐 — 마이그레이션 체계 자체가 없다)
2. 기존 볼륨 업그레이드 경로 (`docker compose down -v` 없이)
3. 승인 (`docs/guide/github-team-guide.md` 절차)

**선결과제:** 마이그레이션 체계 부재는 Phase 2의 실질 첫 관문이다. P2-1보다 먼저 정해야 한다.

### 4.1 코드로 풀 수 없는 전제

§5.3은 악성 연산·OOM을 MVP **미완화**로 두고 "팀 Node 신뢰"에 의존한다. 테넌트 데이터가 들어오는 순간 이 전제가 사라진다.
그리고 §8.3에 따르면 P2–3의 지불 주체는 **조직 IT/보안**이다 — 즉 Phase 3는 기술 완성도가 아니라 **고객 1곳**이 관문이다.

|------|------|-----------------|
| 법무 킥오프 | 계약·책임 | ❌ |
| 격리 초안 | 설계 + 운영 | 부분 |

기획서 §13: 시장 근거가 비어도 기술 Go는 가능하나, **"고객 대화 0건"이면 Product Track 착수 보류**로 적는다. 현재 인터뷰 실적은 **0건**이다.
